# IPC Contract

All communication between the renderer and the main process goes through the preload
bridge. The renderer calls **methods on `window.api`** (typed as `ElectronAPI`); it never
uses `ipcRenderer` directly. This document lists the underlying channels so the surface is
easy to audit and extend.

- **Invoke channels** are request/response (`ipcRenderer.invoke` ↔ `ipcMain.handle`).
- **Events** are one-way, main → renderer (`webContents.send` ↔ `ipcRenderer.on`), exposed
  as `on*` subscription methods that return an unsubscribe function.

Channel-name constants live in
[`src/shared/constants/ipc-channels.ts`](../src/shared/constants/ipc-channels.ts). A few
newer channels are still raw strings (noted below) and are good first cleanup candidates.

## Server lifecycle

| `window.api` method            | Channel           | Request               | Response                     |
| ------------------------------ | ----------------- | --------------------- | ---------------------------- |
| `listServers()`                | `server:list`     | —                     | `ServerWithStatus[]`         |
| `getServer(id)`                | `server:get`      | `string`              | `ServerWithStatus \| null`   |
| `createServer(input)`          | `server:create`   | `CreateServerInput`   | `ServerInstance`             |
| `startServer(id)`              | `server:start`    | `string`              | `void`                       |
| `stopServer(id)`               | `server:stop`     | `string`              | `void` (graceful; kill after 2 min; resolves once exited) |
| `restartServer(id)`            | `server:restart`  | `string`              | `void` (stop, wait for exit, start; starts a stopped server) |
| `updateServerSettings(id, settings)` | `server:update-settings` | `{ serverId, settings: UpdateServerSettingsInput }` | `ServerWithStatus` |
| `deleteServer(id)`             | `server:delete`   | `string`              | `void`                       |

`UpdateServerSettingsInput` is
`{ restartSchedule?: string \| null, backupSchedule?: string \| null, backupKeep?: number }`:
`"HH:MM"` (24-hour, local time) schedules a daily restart or a daily backup, `null` turns it off,
and an omitted field is left unchanged. `backupKeep` is how many scheduled backups are kept, a
whole number from 1 to 365 (default 7). `ServerWithStatus.backupLastRun` is a JSON string
`{ at, outcome: 'ok' | 'skipped' | 'missed' | 'failed', message? }` describing the last scheduled
backup, or `null`; read it with `parseScheduledBackupResult` (`src/shared/utils/backup-schedule.ts`).
Any other value for it is rejected; other keys are ignored. `ServerInstance.restartSchedule` holds the stored value.

`createServer` downloads the server jar (vanilla from Mojang, or the complete Paper/Purpur/Folia
build), verifies its checksum, writes `server.properties` + `eula.txt`, and installs the mod
loader if one was requested. `CreateServerInput` has an optional `jvmProfile`
(`'default' | 'aikar'`), and `ServerInstance` includes `jvmProfile`. The main process validates the
input: name, version, RAM format (`4G` or `4096M`), min RAM not above max RAM, known engine, known
JVM profile, and a build number for plugin platforms.

## Backups

| `window.api` method                         | Channel          | Request                              | Response       |
| ------------------------------------------- | ---------------- | ------------------------------------ | -------------- |
| `listBackups(serverId)`                     | `backup:list`    | `string`                             | `BackupInfo[]` (newest first) |
| `createBackup(serverId)`                    | `backup:create`  | `string`                             | `BackupInfo` (resolves when the backup is complete) |
| `deleteBackup(serverId, backupId)`          | `backup:delete`  | `{ serverId, backupId }`             | `void`         |
| `restoreBackup(serverId, backupId, options?)` | `backup:restore` | `{ serverId, backupId, options? }` | `void` (server must be stopped) |

`options` is `{ backupFirst?: boolean }` (default `true`: back the current files up first).
Backup ids are generated by the main process (`YYYYMMDD-HHMMSS-manual`, `-pre-restore` or
`-scheduled`, UTC) and any other value is rejected. `createBackup` always makes a `manual` backup:
scheduled ones, and the deletion of old ones that goes with them, are started by the main process
only. `createBackup` rejects with a message containing `Cancelled` when
the server is stopped, restarted or deleted, or the app exits, while it runs.

## Console

| `window.api` method             | Channel                  | Request                        | Response            |
| ------------------------------- | ------------------------ | ------------------------------ | ------------------- |
| `sendCommand(id, command)`      | `console:send-command`   | `{ serverId, command }`        | `boolean`           |
| `getServerLogs(id)`             | `console:get-logs` ¹     | `string`                       | `ServerLogEntry[]`  |
| `watchTelemetry(id)`            | `telemetry:watch`        | `string`                       | `void`              |

¹ raw-string channel.

`watchTelemetry(id)` says that a server's numbers are on screen. The tick time in
`ServerTelemetry.tick` is only asked of the server while this is repeated (the server page does
so every 5 seconds; one call counts for 15); CPU, memory and players are reported regardless.
`tick.at` is when the server answered: a consumer must not show an old sample as current.

## System

| `window.api` method          | Channel                    | Request  | Response                |
| ---------------------------- | -------------------------- | -------- | ----------------------- |
| `getJavaInstallations()`     | `system:get-java`          | —        | `JavaInstallation[]`    |
| `selectDirectory()`          | `system:select-directory`  | —        | `string \| null`        |
| `openExternal(url)`          | `system:open-external`     | `string` | `void`                  |

`openExternal` only accepts `http:` and `https:` URLs; anything else is rejected.
Mod loaders are installed by the main process as part of server creation, so there is no
renderer-facing "install loader" channel: the renderer never passes a filesystem path to install into.

## Mod loaders & mods

| `window.api` method                                   | Channel                        | Notes                          |
| ----------------------------------------------------- | ------------------------------ | ------------------------------ |
| `getModLoaderVersions(loader, mcVersion)`             | `modloader:get-versions`       | `{ version, stable }[]`; also accepts `paper`, `purpur`, `folia` (build numbers) |
| `getServerSoftwareVersions(platform)`                 | `server-software:get-versions` | `string[]`; `platform` is `'paper' \| 'purpur' \| 'folia'` |
| `searchMods(options)`                                 | `mod-manager:search` ¹         | `ModSearchResponse`            |
| `getMod(source, id)`                                  | `mod-manager:get` ¹            | `UnifiedMod` + `descriptionHtml` |
| `getModVersions(source, id, gameVersion?, loader?)`   | `mod-manager:get-versions` ¹   | `UnifiedModVersion[]`          |
| `getInstalledMods(id)`                                | `mod-manager:get-installed` ¹  | installed mod rows             |
| `installMod(id, source, projectId, versionId)`        | `mod-manager:install` ¹        | `void`                         |
| `uninstallMod(id, modDbId)`                           | `mod-manager:uninstall` ¹      | `void`                         |
| `toggleMod(id, modDbId, enable)`                      | `mod-manager:toggle` ¹         | `void`                         |

¹ raw-string channel. `source` is `'modrinth' | 'curseforge'`.

`getServerSoftwareVersions` returns the Minecraft versions the platform has builds for, newest
first, and rejects for an unknown platform. For plugin platforms, `installMod` and the related
calls use the server's `plugins/` folder, and only `modrinth` is accepted.

## Remote hosts

| `window.api` method                                  | Channel                    | Request                          | Response                 |
| ---------------------------------------------------- | -------------------------- | -------------------------------- | ------------------------ |
| `listHosts()`                                        | `hosts:list`               | —                                | `RemoteHost[]`           |
| `addHost(input)`                                     | `hosts:add`                | `AddHostInput`                   | `RemoteHost`             |
| `removeHost(id)`                                     | `hosts:remove`             | `string`                         | `void`                   |
| `hostInfo(id)`                                       | `hosts:info`               | `string`                         | `HostInfo`               |
| `listRemoteServers(id)`                              | `hosts:servers`            | `string`                         | `RemoteServer[]`         |
| `createRemoteServer(hostId, input)`                  | `hosts:create-server`      | `{ hostId, input }`              | `RemoteServer`           |
| `startRemoteServer(hostId, serverId)`                | `hosts:start`              | `{ hostId, serverId }`           | `void`                   |
| `stopRemoteServer(hostId, serverId)`                 | `hosts:stop`               | `{ hostId, serverId }`           | `void`                   |
| `restartRemoteServer(hostId, serverId)`              | `hosts:restart`            | `{ hostId, serverId }`           | `void` (returns once msmd accepted it) |
| `updateRemoteServer(hostId, serverId, settings)`     | `hosts:update-server`      | `{ hostId, serverId, settings }` | `RemoteServer`           |
| `deleteRemoteServer(hostId, serverId)`               | `hosts:delete-server`      | `{ hostId, serverId }`           | `void`                   |
| `sendRemoteCommand(hostId, serverId, command)`       | `hosts:command`            | `{ hostId, serverId, command }`  | `void`                   |
| `remoteServerLogs(hostId, serverId)`                 | `hosts:logs`               | `{ hostId, serverId }`           | `ServerLogEntry[]`       |
| `remoteServerMetrics(hostId, serverId)`              | `hosts:metrics`            | `{ hostId, serverId }`           | `RemoteServerMetrics \| null` |
| `remoteLoaderVersions(hostId, loader, mcVersion)`    | `hosts:loader-versions`    | `{ hostId, loader, mcVersion }`  | `{ version, stable }[]`  |
| `remoteSoftwareVersions(hostId, platform)`           | `hosts:software-versions`  | `{ hostId, platform }`           | `string[]`               |
| `listRemoteBackups(hostId, serverId)`                | `hosts:backups`            | `{ hostId, serverId }`           | `BackupInfo[]`           |
| `createRemoteBackup(hostId, serverId)`               | `hosts:backup-create`      | `{ hostId, serverId }`           | `{ operationId }` (returns once msmd accepted it) |
| `restoreRemoteBackup(hostId, serverId, backupId, backupFirst?)` | `hosts:backup-restore` | `{ hostId, serverId, backupId, backupFirst }` | `{ operationId }` (returns once msmd accepted it) |
| `deleteRemoteBackup(hostId, serverId, backupId)`     | `hosts:backup-delete`      | `{ hostId, serverId, backupId }` | `void`                   |

`remoteSoftwareVersions` asks the host's `msmd` daemon (`GET /v1/software/{platform}/versions`) for
the Minecraft release versions the platform has builds for, newest first; `platform` is
`'paper' | 'purpur' | 'folia'`. `remoteLoaderVersions` also accepts these platforms and returns
build numbers. `CreateRemoteServerInput` has an optional `jvmProfile` (`'default' | 'aikar'`) and
its `modLoader` may be `paper`, `purpur` or `folia` (with `modLoaderVersion` as the build number).
A host running an older `msmd` has no `/v1/software` endpoint and rejects the new engines, so
`hosts:software-versions` and such deployments fail until the daemon is updated; an older daemon
silently ignores `jvmProfile`. Plugin installation and management are local-only; remote hosts have no
mod or plugin browser.

**Remote backups** are made, kept and restored by `msmd` on the host; nothing is transferred to
the app. `createRemoteBackup` and `restoreRemoteBackup` only start the operation and resolve with
its id. There is no progress event: `RemoteServer.operation` (`{ id, kind, phase, doneBytes,
totalBytes }`, `phase` is `saving`, `copying` or `replacing`) is present while one runs, and
`RemoteServer.lastOperation` (`{ id, kind, ok, cancelled?, error?, warning?, backupId?,
finishedAt }`) tells how the last one ended; compare its `id` with the one returned. Poll
`listRemoteServers` to follow it. `lastOperation` is kept in the daemon's memory and is gone
after msmd restarts. `backupFirst` defaults to `true`. Errors carry the daemon's own sentence
(`Stop the server before restoring a backup`, `backup not found`); a host with msmd older than
0.2.0 rejects all four with the "older msmd" message. **Scheduled backups** of a remote server
are settings of the server on the host: `updateRemoteServer(hostId, serverId, { backupSchedule?,
backupKeep? })` (same shapes and checks as `server:update-settings`, the time being on the host's
clock; `restartSchedule` goes through the same call), and `RemoteServer` carries
`backupSchedule?`, `backupKeep?` (absent means 7) and `backupLastRun?` (`{ at, outcome, message?
}`, an object here, not a JSON string: read it with `readScheduledBackupResult`). A
`lastOperation` with `scheduled: true` belongs to a backup the host's schedule started. A host
with msmd older than 0.3.0 refuses these settings with the "older msmd" message. `backupId` must look like a backup id
(`YYYYMMDD-HHMMSS-manual|pre-restore|scheduled`), anything else is rejected before a request is
made.

`remoteServerMetrics` resolves to `null` when the host's msmd has no metrics (older than 0.4.0)
and rejects when the server is not running. Every value in `RemoteServerMetrics`
([`server-metrics.ts`](../src/shared/utils/server-metrics.ts)) but `at` (the host's clock) is
optional. Calling it is what makes the host ask the server for its tick time.

## Events (main → renderer)

Each `on*` method registers a listener and returns an unsubscribe function.

| `window.api` method                | Channel / pattern                | Payload                            |
| ---------------------------------- | -------------------------------- | ---------------------------------- |
| `onServerLog(cb)`                  | `event:server-log`               | `ServerLogEntry`                   |
| `onServerStatusChanged(cb)`        | `event:server-status-changed`    | `{ serverId, status }`             |
| `onTelemetry(serverId, cb)`        | `server-telemetry:<serverId>` ¹  | `ServerTelemetry`                  |
| `onUpdateDownloaded(cb)`           | `event:app-update-downloaded`    | `version: string`                  |
| `onShuttingDown(cb)`               | `event:app-shutting-down`        | `serverCount: number`              |
| `onBackupProgress(cb)`             | `event:backup-progress`          | `BackupProgress`                   |

`event:backup-progress` is sent for every backup and restore, whoever started it (a window or the
schedule). The last event of each operation has `phase: 'done'`, whether it succeeded or not (the backup
made before a restore is part of the restore and has no `done` of its own).

¹ per-server raw-string channel.
